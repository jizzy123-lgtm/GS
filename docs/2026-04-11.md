# Mobile Frontend API Integration Guide: Maintenance & Feedback Flow

This report summarizes the backend changes implemented to support the full Maintenance Request lifecycle and the new simplified Feedback system.

## 1. Maintenance Status Reference

Use these IDs to handle UI logic (for example, hiding/showing buttons):

| ID | Name | Description |
|---|---|---|
| 1 | Pending | Initial submission. |
| 2 | Approved | Fully approved by both Head and Director. |
| 4 | Done | Request marked as completed by Staff. |
| 8 | Completed | Internal legacy status. Ignore if visible. |
| 9 | Scheduled | Staff has assigned a date and technician. |

## 2. Updated Endpoints & Payloads

### A. Approval Flow (Sequential)

The two-step approval is now split into distinct endpoints for better role-based control.

#### Head Approval
- URL: `PUT /api/maintenance-requests/{id}/approve-head`
- Role: Head (`2`)

#### Director Approval
- URL: `PUT /api/maintenance-requests/{id}/approve-director`
- Role: Director (`5`)
- Rule: Only callable after Head approval.

### B. Scheduling (NEW & TEMPORARILY MODIFIED)

Assignment of date and technician by staff.

`WARNING`  
Temporary workaround is active: for testing/immediate feedback purposes, calling this endpoint currently skips `Scheduled (9)` and immediately marks the request as `Done (4)`. It also triggers the `maintenance_request_done` push notification right away to prompt the user for feedback.

- URL: `POST /api/maintenance-requests/{id}/assign-schedule`
- Method: `POST`
- Payload:

```json
{
  "scheduled_date": "YYYY-MM-DD",
  "scheduled_time": "HH:MM",
  "assigned_staff": 12,
  "scheduled_notes": "Optional notes from staff"
}
```

### C. Marking as Done (Currently Bypassed)

- URL: `PUT /api/maintenance-requests/{id}/mark-done`
- Rule: This endpoint is currently bypassed by the temporary workaround above, but normally handles moving `Scheduled -> Done`.

## 3. Feedback System (Simplified)

The complex CSMS form is replaced. Use this simple payload:

- URL: `POST /api/feedback`
- Payload:

```json
{
  "request_id": 101,
  "maintenance_request_id": 101,
  "rating": 5,
  "comment": "Great work!"
}
```

Rules:
- Request must be `Done` (status `4`).
- Prevents duplicates: returns `409 Conflict` if feedback was already submitted.

## 4. Response Enhancements

The following fields are now included in all request detail and list responses (`indexWithDetails`, `staffpov`, `headpov`, `directorpov`):

| Field | Type | Description |
|---|---|---|
| `has_feedback` | Boolean | `true` if feedback already exists; use this to hide "Leave Feedback". |
| `scheduled_date` | String | The date assigned to the request. |
| `scheduled_time` | String | The time assigned to the request. |
| `assigned_staff_id` | Integer | User ID of the assigned technician. |

## 5. Summary Tracking

- `TC-5-006`: `GET /api/feedbacks` is now restricted to Admin only.
- Unique constraint: database now enforces one feedback per maintenance request at schema level.

# Frontend Fix Documentation (2026-04-11)

This section documents all frontend changes completed on **April 11, 2026** for admin feedback flow reliability and backend-aligned feedback mapping.

## 6. Bug Fix: Admin Back Navigation Loop (Feedbacks -> Requests Bounce)

### 6.1 Reported Behavior

When an Admin opened a feedback item and pressed Back, the app unexpectedly navigated to request-related screens. Pressing Back again could repeat the behavior, creating a loop-like experience.

### 6.2 Root Cause

Notification deep-link routing logic trusted notification payload `role_id` before the authenticated user role.  
If payload role context differed from the currently logged-in account (for example requester-oriented notification data on an admin session), route resolution could incorrectly redirect to `ViewRequestStatus`.

### 6.3 Fix Implemented

Routing now prioritizes the authenticated session role first, and only falls back to payload role when needed.

#### Files Updated
- `app/(tabs)/index.tsx`
- `app/screens/index.tsx`
- `utils/notificationNavigation.js`

#### Core Adjustment
- Before:
  - `roleId = payloadRole ?? userRole`
- After:
  - `roleId = userRole ?? payloadRole`

This prevents admin navigation from being hijacked by mismatched notification payload roles.

### 6.4 Verification

- Lint validation passed for the edited navigation files.
- Expected runtime behavior:
  1. Admin opens `Feedbacks`
  2. Opens a feedback detail
  3. Presses Back
  4. Returns to feedback list/dashboard without forced jump to request screens

## 7. Feedback Deliverance Fix: Backend Field Mapping Alignment

### 7.1 Backend Contract (Confirmed)

Feedback detail responses now expose clean fields:

```json
{
  "id": 3,
  "maintenance_request_id": 45,
  "rating": 5,
  "comment": "123 test"
}
```

Required frontend binding:
- Rating UI -> `rating`
- Comment UI -> `comment`
- Do not depend on legacy fields such as `sqd0`, `sqd1`, or `suggestions`

### 7.2 Issue in Frontend

Admin feedback display was pulling from aggregated list/embedded structures and could miss or blank out feedback values depending on response shape.

### 7.3 Fix Implemented

`FeedbacksScreen` now fetches and maps detail data per selected request via:
- `GET /api/feedbacks/{id}/details`

and explicitly binds:
- `selectedFeedback.rating`
- `selectedFeedback.comment`

with a normalized mapping helper that supports wrapped responses (`data`) while still preferring clean fields.

#### Files Updated
- `app/screens/FeedbacksScreen.jsx`

#### Key Changes
- Added detail fetch when selecting a feedback entry.
- Added explicit mapping helper for:
  - `rating`
  - `comment`
  - `created_at` / `date_submitted`
  - submitter name
- Removed legacy-biased comment fallback in request-embedded mapping so `comment` is authoritative.
- Added loading indicator while detail payload is being fetched.

### 7.4 POST Payload Compliance Check

Feedback submission payload in requester flow is now aligned to backend expectation:

```json
{
  "request_id": 45,
  "rating": 5,
  "comment": "123 test"
}
```

#### File Updated
- `app/screens/FeedbackScreen.jsx`

#### Adjustment Made
- Send `request_id` (numeric).
- Send trimmed `comment`.
- Keep `rating` as integer 1..5.
- Retains handling for `409 Conflict` (already submitted).

## 10. Notes / Risk

- `FeedbacksScreen` detail fetch currently calls `/feedbacks/{selected.id}/details` where `selected.id` is the request id shown in admin list. This assumes backend route resolves details by request-linked identifier in this context.
- If backend strictly expects feedback record id (not request id), frontend should switch to using the `feedback.id` captured from `/feedbacks` list mapping. The current implementation includes fallback display from list/request-embedded data to reduce blank states if route semantics differ.
